# AI 顧問與 PM 的六個工作入口

每次選一個與當下決策相符的入口。先讓 Agent 讀取 Repo 的 `SKILL.md`，再貼入下列指令，將方括號換成實際資料。

## 1 把 AI 轉型需求縮小成可處理的題目

技法全文：[#44 分割煩惱](../references/techniques/044-problem-slicing.md)

```text
使用 pm-thinking #44。
客戶目前的說法：［原始需求］
發生的情境：［誰、何時、在哪個流程］
限制：［時間、資源、可取得資料］
把問題按時間、場所或條件切片，指出各切片缺哪些資訊。
依已知限制提出一個優先探索的切片，說明理由與尚未驗證之處。
```

適合帶進需求訪談。切片後若已能安排訪談，就先完成這一步。

## 2 預演主管會追問的問題

技法全文：[#31 模擬批評](../references/techniques/031-executive-critique.md)

```text
使用 pm-thinking #31。
提案：［內容］
這場會議要決定：［核准試點／預算／採購／其他］
已知評估標準與資料：［內容］
模擬財務、資訊、營運主管的追問。
每題列出背後關切、目前可回答的部分、必須補的證據。
缺資料時不要編造數字；不要把模擬當作主管真實意見。
```

適合提案前自我檢查。先補最可能改變決策的證據。

## 3 找出 AI Agent 專案會在哪裡失敗

技法全文：[#30 檢測風險](../references/techniques/030-risk-review.md)

```text
使用 pm-thinking #30 的風險檢視。
方案：［功能、使用者、流程、會操作的系統］
成功條件：［怎樣才值得上線］
已知限制：［資料、權限、成本、責任分工］
找出主要失敗原因、影響、緩解措施及剩餘風險。
區分資料已支持的問題與待驗證假設。
若核心風險仍無解，提出縮小範圍或暫緩的條件。
```

適合在承諾建置範圍前使用。緩解措施仍需由實際負責人驗證。

## 4 工作坊結束後整理點子

技法全文：[#21 團隊的創造力](../references/techniques/021-idea-clustering.md)

```text
使用 pm-thinking #21，先統一格式，再分群。
以下每個點子有原始 ID：［貼上清單］
保留每個 ID、原意與關鍵差異；相近的點子可以同群但不要直接合併。
給出群組名稱、各群包含的 ID，以及尚不能歸類的項目。
這次只整理，不評分、不產生 PRD。
```

適合把會議白板轉成可追溯的討論材料。

## 5 判斷 Demo 是否值得進入試點

技法全文：[#37-2 驗證測試的步驟](../references/techniques/037-validation-test.md)

```text
使用 pm-thinking #37-2。
服務或機制：［內容］
最重要的假設：［例如能降低包含人工查核的總處理時間］
受測對象與樣本取得方式：［內容］
資源限制：［內容］
設計最小驗證，包含比較基準、操作步驟、觀察指標、停止條件。
沒有依據的門檻標示為待協議，不假裝已有基準數據。
把流程有效、有人願意使用、有人願意付費分開處理。
```

適合試點規劃。先測會讓整個方案不成立的關鍵假設。

## 6 用一頁說清楚產品價值

技法全文：[#33 發布未來的報導](../references/techniques/033-future-press-release.md)

```text
使用 pm-thinking #33，寫一份內部討論用的未來新聞稿。
概念：［內容］
目標使用者：［內容］
目前的替代做法：［內容］
已知證據與限制：［內容］
說清使用情境、承諾的價值及實現它所需的條件。
明確標示這是未來情境；避免沒有依據的成效數字。
沒有真實訪談就省略客戶引言，或明確標示假想引言。
```

適合對齊產品方向。價值敘事完成後，是否需要驗證取決於接下來要做的決策。
