# 與 Matt Pocock Skills 協作

本指南串接產品思考與工程工作，保留各技能的責任、啟動方式與版本。它是可選整合：沒有安裝外部技能時，pm-thinking 仍可獨立使用。

適用於使用者要求搭配 Matt Pocock Skills，或目前任務需要研究、可操作原型、術語建模及工程交接。單純發想、歸類或短稿不必讀取本指南。

## 本機優先，不需 clone

整合的前提是能取得選定技能及其必要支援檔，不是擁有完整上游 Git 儲存庫。使用環境已提供的技能清單與安裝位置定位，不掃描整個檔案系統或重新查詢 GitHub。

- **已安裝：**直接載入該本機技能；需要相依文件時只讀相關檔案。
- **同一對話已載入且內容仍在上下文：**沿用已有內容，不重讀來確認。檔案有變更、上下文已缺失或需要先前未讀的支援檔時，才補讀必要部分。
- **未安裝：**依下方缺少能力的規則完成可用部分。只有使用者要求安裝、更新、比較上游或排查版本問題時，才針對缺口存取上游；不自動 clone。

本指南內的 GitHub 連結是來源註記，**不是待讀清單**。一般執行不開啟這些連結、不檢查上游更新，也不比對所有技能版本。Clone 只提供本機來源副本；把整份 Repo 讀進上下文仍會增加成本，因此即使已有 clone 也維持按需讀取。

## 載入與啟動界線

1. **定位本機可用技能。**從目前環境已提供的技能清單找到名稱與來源，使用實際安裝版本的說明；不要求每次查版本號、commit 或與上游比對。不要把上游連結當成已安裝能力，也不要為了完成 PM 回答自動安裝或更新。
2. **按需載入一個合作技能。**對可由模型呼叫的技能，使用環境提供的技能載入工具；若環境以讀取 SKILL.md 取代工具，依其正式機制載入。遵循該版本的相依檔案與工具要求，不硬編碼另一台電腦的路徑。
3. **保留使用者入口。**查閱的上游版本將 `to-spec`、`to-tickets`、`implement` 等設為使用者啟動。本指南只準備交接，不能自行呼叫它們，亦不能以直接讀取檔案繞過啟動限制。使用者已明確指定該技能時沿用已有授權，不重複詢問。
4. **不要把階段串成自動流程。**要求釐清產品問題，不代表要求發布規格、建立遠端 issue、實作、commit 或 push。若使用者已授權其中某階段，就在該範圍內完成，不另加例行確認。
5. **處理缺少能力的情況。**合作技能未安裝或缺少必要工具時，簡短說明，繼續完成可用的 PM 分析與交接材料；不得聲稱已執行該技能。原型或查證確實需要缺少的工具時，指出具體未完成部分。
6. **沿用專案設定。**工程入口若需要 issue tracker、標籤或文件位置，先讀專案已有設定；缺少時指出需要設定之處，保留本地交接材料，不自行猜測遠端專案。

上游明確區分可由模型呼叫與只由使用者啟動的技能，規則見 [invocation.md](https://github.com/mattpocock/skills/blob/main/.agents/invocation.md)。這裡描述的是該技能庫的整合規約，不宣稱每個 Agent 平台都有相同的載入工具。

## 一次只由一個流程主導

一般 PM 任務依 [pm-thinking](../../SKILL.md) 的範圍與停止條件執行。進入深入訪談時由 grilling 主導問題順序，PM 技法只在需要時補充分析；不要雙重提問，也不要重新要求已確認的答案。

研究或原型回來後，先判斷它回答了什麼、還缺什麼。只有新證據改變決策時才回到對應 PM 方法；沒有剩餘問題就交付結果。不要形成「PM → grilling → PM」無限循環。

## 決策摘要與交接

只在確實需要跨技能或跨階段交接時整理。能從目前對話取得的資訊直接沿用，不為填滿欄位重新訪談。一般先在回覆中提供；使用者或專案流程需要保存時再寫檔。

```markdown
# 決策摘要：<主題>

## 問題與受眾
誰在什麼情境遇到什麼問題；要做出的決策。

## 證據與假設
- 已知：觀察或資料，以及可追溯來源。
- 假設：尚未驗證的原因、需求、數字或預測。

## 選定方案與理由
已確認的決定、重要取捨，以及仍在比較的選項。

## 本次範圍
要完成的結果，以及明確不做的事。

## 判讀與驗收
產品實驗：成功、失敗或證據不足的判讀方式。
工程交付：可觀察、可驗收的行為。

## 未知與下一步
尚未解決的問題、需要的能力及下一個負責階段。
```

此摘要是工程規格的輸入，不取代 `to-spec` 的格式、測試位置討論或專案設定。不要把假設在交接時升格成已驗證需求。

## 影片轉簡報的例子

使用者想知道小型設計工作室是否需要這個服務：先用 #48 整理既有工作摩擦，再依需要用 #37 設計人工交付與實際報價測試。若只是三個訪談題目，到此就交付，不自動開始工程。

如果問題變成「設計師看得懂逐頁的來源時間標記嗎」，把這個問題、觀察任務與判讀標準交給 prototype 做可操作示範。原型回答可用性問題，仍不能證明願意付費。

待使用者決定實作時，交接「需要可編輯簡報與逐頁來源標記」等已確認決策、證據及不做範圍。使用者選擇啟動 to-spec／to-tickets／implement 中適合的入口；小任務不強迫跑完全部階段。

## 版本與維護

本指南依 2026-10-24 查閱的上游 `main` 撰寫，連結指向上游目前版本，不是固定 commit。執行以當前載入的本機技能為準；以下差異供安裝、升級或版本排查時參考，不要求日常重新查證上游。

建立指南時觀察到的版本差異：

- 本機 `domain-modeling` 使用 `CONTEXT.md`，查閱的上游使用 `GLOSSARY.md`。
- 本機 `grilling` 一次問一題，查閱的上游按相依決策分輪提問。
- 本機 `prototype` 的邏輯分支描述終端互動示範，查閱的上游描述單一 HTML 示範。

不要混用兩個版本的檔名或流程。沿用已選版本及專案文件慣例；同名技能有多個來源而會影響執行時，先確定使用哪一份。僅串接技能不需要搬移詞彙文件、覆蓋全域技能或更新整個套件。

維護時只更新本指南及必要入口。56 個技法的原始 Prompt 保持完整；合作技能仍由各自來源維護。
